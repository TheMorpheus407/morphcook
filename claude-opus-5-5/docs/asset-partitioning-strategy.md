# Asset partitioning strategy

The corpus ships inside the app bundle and is split so launch only parses
what the first screen needs.

## Files

| File | Loaded | Contents |
|---|---|---|
| `partition-manifest.json` | launch | partition registry: id, file, kind, load mode, recipe count, dish ids, byte size; cross-references; loading strategy; corpus version |
| `dishes.json` | launch | every dish concept with `partition_id`, `secondary_partitions`, `cuisine_tags`, `frequency_tier` |
| `ontology.json`, `ingredients.json`, `ingredient-guide.json`, `faqs.json` | launch | shared reference data |
| `search-index.json` | launch | token → recipe ids per language, plus recipe → partition routing |
| `core-recipes.json` | **eager** | high-frequency dishes (most of what people cook) |
| `cuisine-italian.json`, `cuisine-asian.json`, `cuisine-middle-eastern.json` | lazy | mid-frequency dishes grouped by cuisine for discovery |
| `extended-recipes.json` | lazy | rarely used dishes |

Each recipe lives in exactly one partition (its dish's `partition_id`), so
nothing is duplicated. `secondary_partitions` lists partitions that also *surface*
a dish for discovery (e.g. Alfredo is stored in `core` and cross-referenced from
`cuisine-italian`). The manifest's `cross_references` is the inverted view.

## Loading

1. **Launch** — `CorpusRepository.init()` loads the shared files and every
   partition marked `eager` (`core`).
2. **Idle prefetch** — about 400 ms after the first frame, the remaining
   partitions load one at a time, yielding between them.
3. **On demand** — opening a dish awaits its partition (`ensureDish`); a search
   resolves hits through the index's routing table and loads only the
   partitions that contain them (`ensureRecipes`). Concurrent requests share one
   in-flight future.

## Updating

Partitions are generated by `app/tool/build_corpus.dart` from the authored
sources in `app/tool/corpus/`. Moving a dish between partitions is a one-line
change to its `partition` and a rebuild. User data only stores recipe ids, so
repartitioning never needs a migration.
